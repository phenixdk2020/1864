# PROJECT 1864 — v00.00.09f30b

## Higher Command HQ — Division, Brigade, Regiment, Battalion

Status: **TEST IMPLEMENTED / UNITY QA REQUIRED**.

F30B introduces the higher-command structure before artillery is added, so cavalry and artillery are not forced into the infantry battalion/regiment hierarchy. The implementation deliberately reuses the proven lower command layers instead of creating a second company movement system.

## Command chain

The tactical command hierarchy is:

`DIVISIONSCHEF -> BRIGADECHEF -> OBERST/OBERSTLØJTNANT -> MAJOR -> KAPTAJN`

NATO/OOB echelon language for the current prototype is:

`XX Division -> X Brigade -> III Regiment -> II Battalion -> I Company/eskadron/batteri`

Roles are command appointments. Historical officer rank/name remains scenario/OOB data and must not be hard-coded as identical to the command role.

## Organic parent vs attachment

F30B adds `PrototypeCommandAttachment09F30B` with:

- `OrganicParent`: permanent OOB parent;
- `CurrentCommandParent`: HQ currently exercising tactical command;
- `AttachmentType`: `Organic / Attached / Detached / Reserve`.

Infantry companies remain organic to their battalion and regiment. Cavalry and artillery are independent arms and must not be modelled as extra infantry companies under a Major.

In the current prototype:

- `1. Regiment` is organic under `1. Brigade`;
- Gardehusar and Dragon retain a higher cavalry/division organic identity;
- both cavalry units begin tactically attached to `1. Brigade`;
- Brigade HUD can temporarily change their `CurrentCommandParent` to `1. Regiment` and back;
- this changes command ownership/linkage only, not the cavalry movement owner.

The future Kanonbatteri uses exactly the same attachment metadata.

The old separate infantry and cavalry OOB panels are disabled once F30B has installed. F30B presents the chain as one command tree. Single-click selects without moving the camera; double-click selects and places the camera behind the chosen HQ/unit.

## Physical HQ

F30B spawns two physical selectable HQ entities:

- `1. BRIGADE HQ / BRIGADECHEF`;
- `1. DIVISION HQ / DIVISIONSCHEF`.

They auto-follow behind the lower HQ chain with their own higher-HQ movement owner. They do **not** write company routes. Selection shows the relevant higher-command links:

- Division -> Brigade;
- Brigade -> Regiment;
- Brigade/Regiment -> cavalry according to active `CurrentCommandParent`.

## HQ responsibilities

### Divisionschef

- assigns brigade objectives;
- allocates reserve, cavalry and artillery between brigades;
- chooses main effort and broad defensive/attack sectors;
- does not micromanage companies.

### Brigadechef

- assigns missions to regiments;
- allocates attached cavalry/artillery to regimental tasks;
- coordinates combined-arms support;
- maintains brigade reserve.

### Regimental commander

- commands battalions and temporarily attached assets;
- translates brigade mission to battalion missions;
- does not replace local cavalry/artillery commander logic.

### Major

- commands organic infantry companies of one battalion;
- does not permanently own cavalry or artillery.

## Higher mission execution in first prototype

Division and Brigade HUD expose:

`ANGRIB HER / FORSVAR HER / RYK FREM / TILBAGETRÆK / SAML / STOP-HOLD`

F30B currently contains one Brigade and one Regiment. Therefore the execution chain is intentionally:

`Division mission -> Brigade intent -> existing Regimental HQ -> existing Major/Battalion system -> companies`

This makes the hierarchy real without duplicating the lower movement/formation logic. Higher Officer AI is **not autonomous yet**; the player issues higher missions and the existing lower layers execute/decompose them.

## Runtime hardening gate

The F30A Unity log showed repeated runtime exceptions in:

- `PrototypeChargeTargeting09F29K.CaptureLegacyTargetPick`;
- `Regiment.FindNearestEnemyInFireArc`.

F30B adds `PrototypeRuntimeNullGuard09F30B` before normal tactical Update execution. It repairs a transient missing `BattleManager.Instance` reference when a live BattleManager exists, restores missing F29K reflection handles to the F25 charge engine, and disables only the F29K input wrapper if those handles cannot be recovered. The underlying F25 charge engine remains available.

This is a runtime hardening layer; Unity QA must verify that the reported exception spam is actually gone.
