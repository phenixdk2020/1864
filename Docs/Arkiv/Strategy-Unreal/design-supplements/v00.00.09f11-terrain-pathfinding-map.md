# v00.00.09f11 – Terrain/pathfinding/map expansion

Status: IMPLEMENTED FOR TEST

## Purpose

This revision fixes the bridge phase oscillation seen in the 09f10 QA video, introduces a narrow static-obstacle router for houses without re-enabling the old unstable obstacle-navigation stack, expands the battlefield dimensions by 4x in both axes, and extends/widens the river visual across the new map.

## Battlefield scale

- Previous battlefield: **360 x 240 m**.
- 09f11 battlefield: **1440 x 960 m**.
- Linear dimensions are therefore **4x** the previous map.
- Total ground area is **16x** the previous map.
- Scale remains **1 Unity unit = 1 metre**.
- Ground mesh uses 288 x 192 cells (~5 m cell spacing) to keep the expanded test map reasonably light.
- RTS camera bounds, zoom ceiling, move speed and far clipping plane are expanded to cover the full map.

## River

- The visible river now spans almost the full 960 m map depth rather than only the original ~240 m test area.
- Visual river width is increased from about 2.8 m to **4.4 m**, matching the current river hard-blocker width (~2.2 m half-width).
- The bridge remains the only legal crossing in the current prototype.
- River routing remains a higher-priority movement constraint than static building routing.

## Bridge oscillation fix

The 09f10 video showed repeated Console transitions:

`APPROACH_BRIDGE -> CROSS_BRIDGE -> APPROACH_BRIDGE -> CROSS_BRIDGE`

Cause: after CROSS_BRIDGE started, moving more than the arrival tolerance away from the near-entry point caused the generic approach test to become true again, sending the regiment back toward near entry.

09f11 changes the bridge traversal to a strict one-way state machine:

1. `STAGE_BRIDGE`
2. `APPROACH_BRIDGE`
3. `CROSS_BRIDGE`
4. `EXIT_BRIDGE`
5. `DIRECT`

Once `CROSS_BRIDGE` has started, it may not fall back to `APPROACH_BRIDGE`.

The company remains in Column through the bridge corridor and normal movement/formation rules resume only after the far staging point is cleared.

## Static hard blockers

09f11 does **not** re-enable the former V1/V3/V4 obstacle-navigation stack. That stack previously caused units to become stuck around scenery.

Instead, `PrototypeStaticObstacleRouting09F11` owns a small explicit blocker set.

Current hard blockers:

- `Farmhouse`
- `Barn`

If a current destination line crosses an approved blocker, the router inserts safe corner waypoints around its expanded footprint and then resumes the original final destination.

Formation clearance differs by formation:

- Column uses a relatively narrow clearance.
- Line uses a much larger clearance approximating the ~48 m company frontage, so the men should not visibly cut through the building even if the company centre misses it.

River/bridge routing has priority over this building router.

## Recommended next terrain decisions

The following should be explicitly approved before being added to the hard-blocker set:

1. **Trees** — recommended as soft terrain rather than hard blockers: slower movement, cohesion penalty, cover/LOS effects.
2. **Fences** — recommended as low obstacles: short crossing delay / cohesion penalty; perhaps hard for cavalry/artillery until a gap is found.
3. **Walls/stone walls** — when added, recommended as hard infantry obstacle unless using a gate/breach/climb order, plus strong cover.
4. **Ditches/embankments** — recommended as terrain-cost features, not simple rectangles.
5. **Additional houses/farm buildings** — hard blockers using the same building router.
6. **Artillery pieces/wagons** — should normally be dynamic units/obstacles, not part of the static building router.
